Problem: The same familyMemberId != null → PatientFamilyMember, else → Patient conditional is copy-pasted across 5 locations in 4 Service files.

Solution: Extract a VisitorResolver module with two methods: resolveVisitor(familyMemberId) and resolveAllergyHistory(familyMemberId). All 4 Services inject it.

  • Locality: allergy-history bug fixed once, not 5 times
  • Interface shrinks: 2 methods replace ~40 lines of duplication
  • Tests hit one module instead of 4

After — queries named & concentrated in Mapper

(findByPatientAndStatus,
findTodayWaiting, etc.)

Problem: 32 ad-hoc LambdaQueryWrapper chains inline in Services — query logic has no name, no interface, no locality.

Solution: Promote recurring patterns to named Mapper methods. Service calls mapper.findByPatientAndStatus() instead of building a wrapper.

  • Locality: query change touches Mapper, not Service
  • Interface: named queries document intent
  • Each query migration is independent — incremental

Solution: Extract a MedicalRecordService that owns "以实际就诊人为中心的病历聚合". Both callers delegate to it.

  • Locality: aggregation logic change in one module
  • Leverage: Agent get_medical_record tool reuses this

Top Recommendation

#1 — Extract VisitorResolver — highest leverage, smallest blast radius.

The visitor/familyMember parsing is duplicated in 5 locations across 4 files. Extracting it into one module is a surgical change: small diff, zero schema impact, immediate locality gain. Naturally pairs with #2 (test fixtures) since VisitorResolver is trivially unit-testable through its seam.

Second: #2 — IntegrationTestBase (ADR-0018 already mandates this for 08b, extend project-wide). Third: #3 — Mapper queries (larger refactor, but each query is independent).
